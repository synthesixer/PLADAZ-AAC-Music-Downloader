# PLADAZ — Implementation Plan

> **เอกสารวางแผนการพัฒนา (Implementation Plan)**
>
> **ภาษา:** ไทย  
> **ชื่อโครงการ:** PLADAZ  
> **สถานะ:** แผนการพัฒนาที่ยืนยันสถาปัตยกรรมและรายละเอียดทางเทคนิคหลักแล้ว (ส่วน UI Design แยกอ้างอิงในเอกสาร Design Direction โดยตรง; คงเหลือ TBA-023 เกณฑ์ตัวเลขประสิทธิภาพ, TBA-026 รายละเอียดการเทียบชื่อเพลง/ศิลปินกับผลค้นหา และ TBA-027 bitrate ของ fallback encode)  
> **เวอร์ชันเอกสาร:** 2.5  
> **แพลตฟอร์มเป้าหมาย:** Windows  
> **ข้อกำหนดสำคัญ:** ห้าม AI เติมข้อมูลที่ไม่มีหลักฐานหรือเปลี่ยนข้อกำหนดที่ระบุว่าเป็น Immutable Requirements โดยไม่ได้รับอนุญาต

---

## 1. วัตถุประสงค์ของเอกสาร

เอกสารนี้เป็นแหล่งอ้างอิงหลักสำหรับ AI และผู้พัฒนาในอนาคตที่ทำงานกับ PLADAZ โดยระบุขอบเขตที่ยืนยันแล้ว โครงสร้างการออกแบบที่ต้องพิจารณา งานที่ต้องดำเนินการ วิธีทดสอบ และข้อมูลที่ยังไม่ตัดสินใจ

เอกสารนี้แยกสถานะของแต่ละหัวข้ออย่างชัดเจน: หัวข้อที่ระบุว่า **ยืนยันแล้ว** ถือเป็นข้อกำหนด ส่วนหัวข้อที่ระบุว่า **Proposal** เป็นเพียงข้อเสนอเพื่อพิจารณา รายละเอียดที่ยังไม่มีข้อมูลเพียงพอต้องคงเป็น `TBA` จนกว่าจะได้รับการยืนยันจากผู้ใช้หรือหลักฐานที่เชื่อถือได้

### ความหมายของสถานะ

- **Immutable Requirement:** ข้อกำหนดที่ผู้ใช้ยืนยันแล้ว ห้ามเปลี่ยน ตัดออก หรือตีความใหม่เอง
- **TBA (To Be Advised / To Be Announced):** ยังไม่ได้กำหนด ต้องถามผู้ใช้หรือศึกษาข้อมูลก่อนตัดสินใจ
- **Proposal:** ข้อเสนอเพื่อพิจารณา ไม่ใช่ข้อกำหนดที่ยืนยันแล้ว
- **Verified:** ตรวจสอบด้วยหลักฐานหรือการทดสอบแล้ว ต้องระบุหลักฐานประกอบ

### 2.1 Metadata ที่ต้องรองรับ

รายการฟิลด์ที่ผู้ใช้ยืนยันให้ PLADAZ รองรับ:

- `Title`
- `Track Artist`
- `Album`
- `Album Artist`
- `Track Number`
- `Disc Number`
- `Year`
- `Genre`
- `Album Art`

**ข้อควรระวัง:** การยืนยันรายการนี้หมายถึงฟิลด์เหล่านี้เป็นเป้าหมายของ Metadata ที่ต้องรองรับ ไม่ได้ยืนยันว่าแหล่งเพลงทุกแห่งจะมีข้อมูลครบ หรือรูปแบบ AAC ทุกชนิดจะจัดเก็บข้อมูลแต่ละฟิลด์ด้วยวิธีเดียวกัน รายละเอียดเชิงเทคนิคต้องตรวจสอบก่อนลงมือพัฒนา

### 2.2 ฟีเจอร์การพัฒนาที่ยืนยันแล้ว (Confirmed Features)

ผู้ใช้ได้ยืนยันข้อกำหนดฟีเจอร์หลักเพิ่มเติมดังนี้:

1. **Download Queue — ระบบคิวดาวน์โหลด**
   - จัดรายการเพลงที่ต้องการดาวน์โหลดหลายเพลงต่อเนื่อง โดยคิวรอกด Start จึงเริ่มประมวลผล พร้อมมีคำสั่ง Cancel และ Resume (DEC-042)
   - แสดงสถานะของแต่ละงานชัดเจน: `Queued`, `Downloading`, `Completed` และ `Failed`
2. **Smart Folder Organizer — จัดโฟลเดอร์อัตโนมัติ**
   - สร้างโฟลเดอร์ด้วยโครงสร้าง `Album Artist / Album`
   - มีกฎจัดการชื่อไฟล์/โฟลเดอร์ซ้ำ
   - มีกฎจัดการอักขระต้องห้ามของ Windows ในชื่อโฟลเดอร์และไฟล์
   - มีกฎจัดการกรณีข้อมูล `Album Artist` หายไป
3. **SD Card Manager — จัดการ Micro SD Card**
   - ตรวจสอบการมีอยู่ของ Micro SD Card และตำแหน่งจัดเก็บที่เลือก
   - ตรวจสอบพื้นที่ว่างบนการ์ดก่อนและระหว่างการบันทึก
   - ตรวจสอบสถานะการเชื่อมต่อ และแจ้งเตือนทันทีหากการ์ดถูกถอดระหว่างทำงาน
4. **Output Validator — ตรวจสอบไฟล์ก่อนแจ้งว่าสำเร็จ**
   - ตรวจสอบว่าไฟล์ผลลัพธ์เปิดอ่านได้จริง (ไม่เสียหายหรือเขียนไม่สมบูรณ์)
   - ตรวจสอบรูปแบบเสียงถูกต้องตามเป้าหมาย (AAC)
   - ตรวจสอบ Metadata ตามเงื่อนไขที่กำหนด: บังคับมี `Title` ส่วนฟิลด์อื่นเว้นว่างได้ตามกฎ 7.3 (DEC-030)
   - ตรวจสอบว่ามีปกอัลบั้มตามเงื่อนไข (กรณีหาปกไม่ได้ ให้เป็นไปตามสวิตซ์ใน `config.json` ตามหัวข้อ 7.5 / DEC-031)
   - ปรับสถานะเป็น `Completed` ได้ก็ต่อเมื่อผ่านการตรวจสอบทั้งหมดนี้แล้วเท่านั้น
5. **Automated Regression Testing — รันทดสอบอัตโนมัติเมื่อแก้โค้ด**
   - มีระบบทดสอบอัตโนมัติที่รันซ้ำเพื่อป้องกันการถดถอยเมื่อมีการแก้ไขโค้ด
   - มุ่งเน้นครอบคลุมส่วนสำคัญ: การจัดโฟลเดอร์, การจัดการ Metadata, การจัดการกรณีชื่อซ้ำ และการเขียนไฟล์ลงอุปกรณ์จัดเก็บ

## 4. ขอบเขตของระบบ

### 4.1 ขอบเขตที่ยืนยันแล้ว

1. ทำงานบน Windows
2. ดาวน์โหลดเพลงจาก YouTube / YouTube Music ด้วย `yt-dlp` + `FFmpeg` โดยรองรับการวางลิงก์ทั้ง **เพลงเดี่ยว (Single Track), เพลย์ลิสต์ (Playlist) และอัลบั้ม (Album)** เพื่อแตกเข้าสู่คิวดาวน์โหลด
3. เป้าหมายไฟล์เสียงคือ AAC-LC ใน M4A Container (`.m4a`)
4. รองรับ Metadata ตามรายการในหัวข้อ 2.1 (ดึงจาก `yt-dlp` + เสริมด้วย iTunes/MusicBrainz Search API) และปกอัลบั้มขนาด 1:1 JPEG 800x800 px
5. บันทึกเพลงลง Micro SD Card สำหรับเครื่องเล่น **SNOWSKY ECHO DAP**
6. ให้ผู้ใช้เลือกโฟลเดอร์ปลายทางได้
7. จัดโฟลเดอร์โดยอิง Album Artist และ Album
8. มีโครงสร้างซอฟต์แวร์แบบ Decoupled Frontend-Backend (`pywebview` + Python Core) ที่สามารถขยายต่อได้
9. มีชุดทดสอบสำหรับตรวจสอบพฤติกรรมสำคัญ
10. **ระบบคิวดาวน์โหลด (Download Queue):** จัดรายการเพลงต่อเนื่องแบบ Sequential Worker (ทีละ 1 เพลง) พร้อมแสดงสถานะ `Queued`, `Downloading`, `Completed` และ `Failed`
11. **ระบบจัดโฟลเดอร์อัตโนมัติ (Smart Folder Organizer):** สร้างโฟลเดอร์ตาม Album Artist / Album พร้อมกฎชื่อซ้ำ (Conflict Prompt Dialog) อักขระต้องห้าม (`_`) และกรณีไม่มี Album Artist / Album
12. **ระบบจัดการ Micro SD Card (SD Card Manager):** ตรวจสอบการ์ด พื้นที่ว่าง ตำแหน่งจัดเก็บ สถานะการเชื่อมต่อ แจ้งเตือนหากการ์ดถูกถอดระหว่างทำงาน และใช้กลไก Temp Staging & Copy & Verify
13. **ระบบตรวจสอบไฟล์ก่อนแจ้งว่าสำเร็จ (Output Validator):** ตรวจสอบไฟล์เปิดอ่านได้ เสียงถูกต้องตามรูปแบบ AAC มี Metadata ตามกฎ (บังคับ `Title`, ฟิลด์อื่นเว้นว่างได้) และมีปกอัลบั้ม (กรณีหาปกไม่ได้เป็นไปตามหัวข้อ 7.5) ก่อนนับเป็น Completed
14. **ระบบทดสอบการถดถอยอัตโนมัติ (Automated Regression Testing):** ใช้ `pytest` รันทดสอบอัตโนมัติเมื่อแก้โค้ด โดยเฉพาะส่วนจัดโฟลเดอร์ Metadata ชื่อซ้ำ และการเขียนไฟล์
15. **ภาษาและทิศทาง UI (`TBA-019`):** ใช้ภาษาอังกฤษ (English) โดยแยกเอกสารด้านการออกแบบ UI ออกจาก `IMPLEMENT_PLAN.md` โดยตรง ให้ศึกษาขอบเขตและทิศทางจาก [`PLADAZ — Design Direction & Handoff.md`](file:///e:/Doc/Code/randombullshit/PLADAZV2/PLADAZ%20—%20Design%20Direction%20&%20Handoff.md) และ [`PLADAZ UI Mockup.html`](file:///e:/Doc/Code/randombullshit/PLADAZV2/PLADAZ%20UI%20Mockup.html) (ข้อกำหนดการนำ Mockup ไปใช้ ดู DEC-028)
16. **การยืนยันสิทธิ์และตัวเลือกขั้นสูง:** แสดงข้อตกลงการใช้งานส่วนบุคคล (Personal Use Disclaimer) ในการเปิดใช้งานครั้งแรก รองรับการแนบไฟล์ `cookies.txt` (Optional) และมีฟีเจอร์อัปเดตโมดูล `yt-dlp` ในแอป

### 4.2 สิ่งที่ยังไม่ถือเป็นข้อกำหนด

รายการต่อไปนี้ยังไม่ยืนยัน จึงห้ามถือว่าเป็นฟีเจอร์ที่ต้องมี:

- ระบบบัญชีผู้ใช้หรือการกรอกรหัสผ่านเข้าสู่ระบบโดยตรงในแอป (ยืนยันเฉพาะการแนบไฟล์ `cookies.txt` แบบ Optional โดยไม่เก็บรหัสผ่าน)
- การดาวน์โหลดต่อจากจุดที่หยุดในระดับไบต์ (Chunk-level Resume)
- การแก้ไข Metadata ด้วยตนเองผ่าน UI (Manual Tag Editor)
- ระบบค้นหาเพลงภายในแอปแบบพิมพ์คำค้นหา (ยืนยันเฉพาะการวางลิงก์เพลงเดี่ยว, Playlist และอัลบั้ม)
- ระบบอัปเดตตัวโปรแกรมหลัก `.exe` อัตโนมัติแบบเต็มรูปแบบ (ยืนยันเฉพาะฟีเจอร์อัปเดตโมดูล `yt-dlp`)
- เกณฑ์เชิงปริมาณด้านประสิทธิภาพและขนาดไฟล์ (`TBA-023`)

รายการเหล่านี้อาจถูกเสนอเพื่อพิจารณาได้ แต่ต้องระบุว่าเป็น `Proposal` และรอการยืนยันก่อนพัฒนา

## 5. แนวทางสถาปัตยกรรม

หัวข้อ 5.1 เป็น **แนวทางออกแบบเบื้องต้น (Proposal)** ส่วนหัวข้อ 5.2 และ 5.3 เป็นเทคโนโลยีและสถาปัตยกรรมที่ยืนยันแล้ว

### 5.1 หลักการออกแบบ

- **Separation of Concerns:** แยก UI, ขั้นตอนการทำงาน, กฎธุรกิจ และการเข้าถึงไฟล์/บริการภายนอก
- **Single Responsibility Principle (SRP):** แต่ละโมดูลควรมีหน้าที่หลักชัดเจน
- **Dependency Inversion Principle (DIP):** กฎธุรกิจไม่ควรผูกกับไลบรารีหรือบริการภายนอกโดยตรง
- **Open/Closed Principle (OCP):** ออกแบบให้เพิ่มแหล่งข้อมูลหรือวิธีประมวลผลใหม่ได้โดยไม่ต้องแก้ทุกส่วน
- **Explicit Error Handling:** ข้อผิดพลาดต้องถูกส่งกลับและบันทึกอย่างเหมาะสม ไม่กลืนข้อผิดพลาดเงียบ ๆ
- **Testability:** ออกแบบให้ทดสอบกฎธุรกิจได้โดยไม่ต้องพึ่ง UI หรืออุปกรณ์จริงทุกครั้ง
- **Traceability:** เชื่อมโยงข้อกำหนดกับโมดูลและ Test Cases ได้

ไม่จำเป็นต้องใช้รูปแบบการออกแบบ (Design Pattern) ทุกชนิด เลือกใช้เฉพาะเมื่อแก้ปัญหาที่ระบุได้จริง

| Smart Folder Organizer | สร้างเส้นทางโฟลเดอร์ตาม Album Artist / Album พร้อมแปลงอักขระต้องห้ามเป็น `_`, ตัดชื่อไม่เกิน 100 อักขระ, จัดการชื่อลงท้ายจุด/ช่องว่างและชื่อสงวน (DEC-034) และ fallback เป็น 'Unknown Artist' / 'Unknown Album' | ขยายจาก IR-011, IR-018 |

| Output Validator | ตรวจสอบไฟล์ผลลัพธ์ใน Temp (เปิดอ่านได้, เป็น AAC ถูกต้อง, Metadata ตามกฎ (บังคับ `Title`), ปกอัลบั้มตามหัวข้อ 7.5) ก่อนคัดลอกเข้า SD Card และแจ้งสำเร็จ | ขยายจาก IR-020 |
| Logging / Error Reporting | ใช้ Python `logging` + `RotatingFileHandler` บันทึกเหตุการณ์แบบจำกัดขนาดไฟล์ และส่ง Structured Error แจ้งบน UI | ยืนยันแล้ว (TBA-017) |
| Configuration & History | เก็บค่าตั้งค่าและประวัติในไฟล์ JSON แบบ Portable (`config.json` / `history.json`) ข้างไฟล์ `.exe` | ยืนยันแล้ว (TBA-015, TBA-018) |
| Automated Regression Test Suite | ใช้ **`pytest`** รันชุดทดสอบอัตโนมัติเมื่อแก้โค้ดเพื่อป้องกันการถดถอย (Folder, Metadata, ชื่อซ้ำ, การเขียนไฟล์) | ขยายจาก IR-021, ยืนยันใช้ pytest |

### 5.3 รูปแบบสถาปัตยกรรม (Decoupled Frontend-Backend Architecture)

ผู้ใช้ได้ยืนยันแนวทางการออกแบบระบบโดยแยก **หน้าบ้าน (Frontend UI)** และ **หลังบ้าน (Python Backend Core)** ออกจากกันอย่างชัดเจน:

1. **Frontend (หน้าบ้าน):** มุ่งเน้นการปฏิสัมพันธ์กับผู้ใช้และการแสดงผล UI โดยทำหน้าที่ส่งคำสั่ง (Request/Command) ไปยังระบบหลังบ้าน ทั้งนี้รายละเอียดด้านการออกแบบ UI แยกอ้างอิงในเอกสาร [`PLADAZ — Design Direction & Handoff.md`](file:///e:/Doc/Code/randombullshit/PLADAZV2/PLADAZ%20—%20Design%20Direction%20&%20Handoff.md) โดยตรง (ตามเงื่อนไขใน `TBA-019`)
2. **Backend (หลังบ้าน - Python Core):** เป็นตัวประมวลผลหลัก (Process Engine) ที่ควบคุมการทำงานของ `yt-dlp`, `FFmpeg`, `mutagen`, `Smart Folder Organizer`, `SD Card Manager` และ `Output Validator`
3. **การสื่อสารระหว่างหน้าบ้านและหลังบ้าน (pywebview Native JS Bridge):** หน้าบ้าน (JavaScript) เรียกใช้ฟังก์ชัน Python โดยตรงผ่าน `window.pywebview.api` และหลังบ้านส่ง Event / Progress อัปเดตกลับไปยังหน้าบ้าน ทำให้ทำงานได้ลื่นไหล ไม่ต้องเปิด Network Port ในเครื่อง และไม่ถูก Windows Firewall บล็อก
4. **การแพ็กเกจและการ Deploy (PyInstaller):** รวมโค้ด Python, Web Assets (HTML/CSS/JS และไฟล์ CSS ที่ build ล่วงหน้าจาก Tailwind) และ Binaries (`bin/ffmpeg.exe`, `bin/yt-dlp.exe` ใน `_internal/bin/`) เข้าด้วยกันเป็นแพ็กเกจพร้อมใช้งาน (Portable Folder / Single `.exe` entry point) โดยยังคงสามารถดาวน์โหลดอัปเดต `yt-dlp.exe` ได้อิสระแบบ in-place (DEC-038, DEC-046) และตัด `ffprobe.exe` ออกเนื่องจากใช้ pure-Python mutagen ตรวจสอบไฟล์ โดยอาศัย Microsoft Edge WebView2 ที่มีอยู่ใน Windows 10/11 อยู่แล้ว ทำให้เครื่องผู้ใช้ไม่ต้องลง runtime เพิ่ม
5. **ความทนทานต่อข้อผิดพลาด (Fault Tolerance):** ข้อผิดพลาดจากระบบหลังบ้านหรือระบบไฟล์ SD Card จะถูกส่งกลับมาเป็น Structured Error เพื่อให้ UI นำไปแสดงผลแจ้งเตือนผู้ใช้ได้อย่างนุ่มนวล ไม่ทำให้ระบบหยุดทำงานโดยสิ้นเชิง

## 6. ข้อกำหนดการจัดโฟลเดอร์

### 6.1 โครงสร้างหลักที่ยืนยันแล้ว

แนวทางโครงสร้างโฟลเดอร์:

```text
<Selected Destination>/
└── <Album Artist>/
    └── <Album>/
        └── <Track File>
```

โครงสร้างนี้แสดงหลักการจัดหมวดหมู่ที่ยืนยันแล้ว ไม่ได้ยืนยันชื่อโฟลเดอร์ราก เช่น `Music` หรือรูปแบบชื่อไฟล์

### 6.2 กฎที่ยืนยันแล้ว (Confirmed Rules)

1. **โครงสร้างโฟลเดอร์หลัก:** ใช้ `Album Artist` เป็นระดับโฟลเดอร์ศิลปิน และ `Album` เป็นระดับโฟลเดอร์อัลบั้ม (`<Destination>/<Album Artist>/<Album>/<Track File>`)
2. **ห้ามใช้ Track Artist เป็นหลัก:** ห้ามใช้ `Track Artist` แทน `Album Artist` ในการสร้างโฟลเดอร์ศิลปิน ยกเว้นเฉพาะกรณี Fallback ตามกฎข้อ 3
3. **กฎเมื่อไม่มี Album Artist หรือไม่มีชื่อ Album สำหรับการจัดโฟลเดอร์ (Folder Fallback Rules):**
   - **ระดับโฟลเดอร์ศิลปิน (Artist Folder):**
     - **Fallback ลำดับที่ 1:** หากไม่มี `Album Artist` ให้ใช้ `Track Artist` มาเป็นชื่อโฟลเดอร์ศิลปินแทน
     - **Fallback ลำดับที่ 2:** หากไม่มีทั้ง `Album Artist` และ `Track Artist` ให้ยัดเข้าโฟลเดอร์ศิลปินชื่อ `'Unknown Artist'`
   - **ระดับโฟลเดอร์อัลบั้ม (Album Folder):**
     - หากไม่มีชื่อ `Album` ให้จัดเข้าโฟลเดอร์ชื่อ `'Unknown Album'` (แต่ในแท็ก Metadata ของไฟล์ให้เว้นว่างไว้ตามกฎ)
4. **การจัดการอัลบั้มที่มีหลายแผ่น (Multi-Disc Handling):**
   - เก็บไฟล์เพลงทั้งหมดรวมอยู่ในโฟลเดอร์ `<Album>` เดียวกัน โดยอาศัยแท็ก `Disc Number` ภายในไฟล์เป็นตัวแยกแผ่นบนเครื่องเล่นเพลง
5. **กฎจัดการอักขระต้องห้ามและความยาวชื่อของ Windows (Sanitization & Length Rule):**
   - อักขระสงวนของระบบไฟล์ Windows ได้แก่ `\ / : * ? " < > |` **และอักขระควบคุม ASCII 0x00–0x1F** จะถูกแปลงเป็นตัวอักขระ `_` (Underscore) เสมอ (DEC-037)
   - ตัดความยาวชื่อโฟลเดอร์และชื่อไฟล์ไม่ให้เกิน **100 อักขระต่อระดับ**
   - **จุดหรือช่องว่างที่อยู่ท้ายชื่อทุกตัว** ให้แปลงเป็น `_` (เช่น `Hello...` → `Hello___`) ตรวจหลังขั้นตัดความยาว 100 อักขระ (DEC-037)
   - ตรวจชื่อสงวนของ Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`) ไม่สนตัวพิมพ์เล็ก-ใหญ่ กับ **ส่วนก่อนจุดแรก** ของชื่อโฟลเดอร์และชื่อไฟล์ หากตรงให้ต่อท้ายส่วนนั้นด้วย `_` เช่น `CON` → `CON_`, `CON.mix` → `CON_.mix` (DEC-037)
   - **การรับมือ Windows MAX_PATH (DEC-043):** การตัด 100 อักขระต่อระดับไม่ได้รับประกันว่าจะไม่เกินเพดาน Windows MAX_PATH ในกรณีสุดโต่ง (เช่น ศิลปิน 100 + อัลบั้ม 100 + ชื่อเพลง 100 + ตัวคั่นและนามสกุล รวมเกิน 306 อักขระ) ระบบยอมรับกรณีสุดโต่งนี้ โดยหลังประกอบเส้นทางเต็ม (รวมถึงกรณี Keep Both) ให้ตรวจความยาวเส้นทาง หากเกิน 259 อักขระ ให้ปรับสถานะงานเป็น `Failed` ด้วยรหัส `ERR_PATH_TOO_LONG` ทันทีก่อนเริ่มดาวน์โหลดเสียง พร้อมข้อความแจ้งเตือนที่เข้าใจได้ และไม่ดาวน์โหลดเสียง
6. **รูปแบบชื่อไฟล์เพลง (Track File Naming):**
   - ใช้รูปแบบ `<Title>.m4a` (ใช้เฉพาะชื่อเพลงอย่างเดียว เรียบง่ายและกระชับ โดยผ่านการแปลงอักขระต้องห้ามและจำกัดความยาว)
7. **นโยบายเมื่อพบไฟล์ปลายทางชื่อซ้ำ (Duplicate File Conflict Policy):**
   - จุดตรวจสอบ: ตรวจหลังได้ Metadata (จึงทราบ Album Artist / Album / Title) และก่อนเริ่มดาวน์โหลดเสียง เพื่อไม่ให้ดาวน์โหลดเสียงที่ผู้ใช้เลือกข้าม (DEC-036)
   - เมื่อตรวจพบว่าไฟล์เพลงมีอยู่แล้วในโฟลเดอร์ปลายทาง ระบบจะแสดงหน้าต่างแจ้งเตือนถามผู้ใช้ (**Conflict Prompt Dialog**)
   - ตัวเลือกการดำเนินการ:
     - **Overwrite (เขียนทับ):** ดาวน์โหลดและบันทึกทับไฟล์เดิม (คัดลอกเป็นไฟล์ชั่วคราวบนการ์ดก่อนแล้วค่อยแทนที่ไฟล์เดิม — DEC-040)
     - **Skip (ข้าม):** เอางานออกจากคิวทันที (ไม่มีสถานะที่ 5 ตาม IR-017) ข้ามการดาวน์โหลดเสียง และคงไฟล์เดิมไว้ (DEC-039)
     - **Keep Both (เก็บไว้ทั้งสองไฟล์):** บันทึกไฟล์ใหม่โดยเติมดัชนีลำดับต่อท้าย เช่น `<Title> (1).m4a`
   - ตัวเลือกเสริม (Checkboxes):
     - `Apply to all in this album` (ใช้ตัวเลือกนี้กับทุกไฟล์ที่ซ้ำและมี **โฟลเดอร์ปลายทางเดียวกัน** กับไฟล์นี้ — DEC-044)
     - `Apply to all in queue` (ใช้ตัวเลือกนี้กับทุกไฟล์ที่ซ้ำในคิวรอบการรันนี้ **รวมงานที่เพิ่มเข้ามาภายหลัง จนกว่าคิวจะว่าง** — DEC-044)

## 7. Metadata และไฟล์เสียง

### 7.1 ฟิลด์ที่ต้องรองรับ

| ฟิลด์ | ความหมายในการใช้งาน | สถานะ |
|---|---|---|
| Title | ชื่อเพลง | ต้องรองรับ |
| Track Artist | ศิลปินของแทร็ก | ต้องรองรับ |
| Album | ชื่ออัลบั้ม | ต้องรองรับ |
| Album Artist | ศิลปินระดับอัลบั้ม และใช้จัดโฟลเดอร์ | ต้องรองรับ |
| Track Number | ลำดับแทร็ก | ต้องรองรับ |
| Disc Number | ลำดับแผ่น | ต้องรองรับ |
| Year | ปีของเพลง/อัลบั้ม | ต้องรองรับ |
| Genre | ประเภทแนวเพลง | ต้องรองรับ |
| Album Art | ปกอัลบั้ม (ฝังลงไฟล์) | ต้องรองรับ |

### 7.2 รายละเอียดทางเทคนิคที่ยืนยันแล้ว

- **Container & Codec:** ใช้ **M4A Container (`.m4a`)** ร่วมกับ Audio Codec **AAC-LC** (Advanced Audio Coding - Low Complexity)
- **เครื่องมือดาวน์โหลดและแปลงเสียง:** ใช้ `yt-dlp` สำหรับดึงสตรีมเสียง โดยเลือกสตรีม AAC (m4a) ก่อน หากมีให้ remux เท่านั้น หากไม่มีจึง encode เป็น AAC-LC จากสตรีมที่ดีที่สุด (DEC-033) ด้วย `FFmpeg` และสกัดภาพปกในโฟลเดอร์ชั่วคราว (Temp Staging)
- **แหล่งข้อมูล Metadata (Primary + Enrichment Fallback):**
  - ใช้ข้อมูลจาก `yt-dlp` (YouTube Music / YouTube) เป็นหลัก
  - เสริมด้วย **iTunes / MusicBrainz Search API** (แบบไม่ต้องใช้ API Key) โดยอัตโนมัติเพื่อค้นหาและเติมฟิลด์ที่มักขาดหายจาก YouTube เช่น `Album Artist`, `Track Number`, `Disc Number` และ `Genre`
  - เงื่อนไขการยอมรับผลค้นหา: ยอมรับเฉพาะผลที่ชื่อเพลงและชื่อศิลปินตรงกับข้อมูลต้นทางจาก `yt-dlp` หากไม่ตรงให้ไม่เติมค่า (เว้นว่างตามกฎ 7.3) รายละเอียดวิธีเทียบ: `TBA-026` (DEC-035)
  - ข้อจำกัดของ MusicBrainz API (ตรวจสอบจาก https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting เมื่อ 2026-10-23): เฉลี่ยไม่เกิน 1 request ต่อวินาทีต่อ IP และทุก request ต้องมี User-Agent ที่ระบุแอปพร้อมช่องทางติดต่อผู้พัฒนา
- **มาตรฐานปกอัลบั้ม (Album Art Specification):**
  - ดึงภาพปกความละเอียดสูงจาก `yt-dlp` หรือ iTunes/MusicBrainz แล้วประมวลผลด้วยไลบรารี `Pillow` แปลงเป็นสัดส่วนจัตุรัส **1:1 ขนาด 800x800 px รูปแบบ JPEG** ก่อนฝังลงใน atom `covr` เพื่อใช้แสดงผลบนหน้าจอ SNOWSKY ECHO DAP (ผลการแสดงผลบนเครื่องจริงรอผลทดสอบ TC-015)
- **เครื่องมือจัดการ Metadata และปกอัลบั้ม:** ใช้ไลบรารี `mutagen` ใน Python สำหรับบันทึกฟิลด์ Metadata ทั้ง 9 รายการลงใน MP4 Tags (ilst atoms)
- **การรักษาข้อมูล:** ต้องบันทึกข้อมูลตัวอักษรด้วย UTF-8 อย่างสมบูรณ์เพื่อรองรับชื่อเพลงและศิลปินภาษาไทย

### 7.3 กฎการบันทึก Metadata เมื่อไม่มีข้อมูลจากต้นทาง (Missing Metadata Rules)

ผู้ใช้ได้ระบุกฎความแตกต่างระหว่างการบันทึกแท็กลงไฟล์ และการสร้างโฟลเดอร์ไว้อย่างชัดเจน:

1. **ฟิลด์ `Album Artist` ในแท็กไฟล์เสียง:**
   - **Fallback ลำดับที่ 1:** หากไม่มี `Album Artist` ให้ดึงค่าจาก `Track Artist` มาบันทึกแทน
   - **Fallback ลำดับที่ 2:** หากไม่มีทั้งคู่ ให้ **เว้นว่างไว้ (Leave blank / omit tag)** ห้ามใส่ข้อความหลอกลงในแท็กของไฟล์
2. **ฟิลด์ Metadata อื่นๆ ทั้งหมด (`Album`, `Track Number`, `Disc Number`, `Year`, `Genre` ฯลฯ):**
   - หากไม่มีข้อมูลจากต้นทาง (และไม่พบจากระบบค้นหาเสริม) ให้ **เว้นว่างไว้ทั้งหมด (Leave blank)**
3. **การแยกความรับผิดชอบ (Metadata vs Folder):**
   - การเว้นว่างในแท็กมีขึ้นเพื่อรักษาความบริสุทธิ์ของข้อมูลเพลง
   - ในขณะที่การจัดโฟลเดอร์บนระบบไฟล์ หากไม่มีศิลปินจะยัดเข้า `'Unknown Artist'` และหากไม่มีชื่ออัลบั้มจะจัดเข้า `'Unknown Album'` เพื่อให้ระบบไฟล์มีโครงสร้างรองรับที่ชัดเจน
4. **การตรวจโดย Output Validator (DEC-030):**
   - ฟิลด์บังคับมีเพียง `Title` ฟิลด์อื่นเว้นว่างได้ตามข้อ 1–2 และไม่ทำให้ไฟล์ Failed

### 7.4 ข้อมูลอุปกรณ์เป้าหมายที่ยืนยันแล้ว (Target Device Profile: SNOWSKY ECHO DAP)

- **รุ่นอุปกรณ์:** **SNOWSKY ECHO DAP**
- **สถาปัตยกรรม DAC:** Dual CIRRUS CS43198 (CS43198 x2)
- **รูปแบบไฟล์เสียงที่อุปกรณ์รองรับอย่างเป็นทางการ:**
  - WAV (สูงสุด 24bit / 192kHz)
  - FLAC (สูงสุด 24bit / 192kHz)
  - APE (สูงสุด 24bit / 192kHz)
  - **M4A** (Native Support), MP3, OGG, WMA
  - DSD64, DSD128, DSD256
- **ข้อสรุปความเข้ากันได้:**
  - ตัวเครื่องรองรับรูปแบบ **M4A** โดยตรงตามสเปกของอุปกรณ์ (ยืนยันจากสเปก ยังไม่ใช่ผลทดสอบ) คาดว่าไฟล์ AAC-LC ใน M4A Container (`.m4a`) พร้อมปก JPEG 800x800 px ที่ PLADAZ สร้างขึ้นจะเล่นได้บนเครื่องนี้ ทั้งนี้ต้องรอผลทดสอบ TC-015 ก่อนถือเป็น Verified

### 7.5 กรณีหาปกอัลบั้มไม่ได้ (DEC-031)

- หากหาปกไม่ได้เลยทั้งจาก `yt-dlp` และ iTunes/MusicBrainz ผลลัพธ์เป็นไปตามสวิตซ์ใน `config.json` ที่ผู้ใช้เลือกได้ในหน้าตั้งค่า:
  - **ค่าเริ่มต้น:** ไฟล์ผ่าน Output Validator ได้ สถานะเป็น `Completed` พร้อมแสดงคำเตือนว่าไม่มีปก
  - **เมื่อผู้ใช้เปลี่ยนสวิตซ์ (บังคับต้องมีปก):** ไม่มีปกถือว่าไม่ผ่าน Output Validator สถานะเป็น `Failed`
- คำเตือนไม่ทำให้เกิดสถานะใหม่ สถานะยังเป็น 4 สถานะตาม IR-017
- ชื่อคีย์ใน `config.json` ยืนยันใช้ `"require_album_art"` แสดงเป็นสวิตซ์ `Require album art` ในหน้า Settings (บอร์ด 06) และแสดงป้ายเตือน `! No cover` คู่กับสถานะ `Completed` (DEC-050)

## 8. การจัดการข้อผิดพลาดและกลไกป้องกันไฟล์เสีย

ระบบออกแบบให้ป้องกันความเสียหายของข้อมูลบน Micro SD Card อย่างรัดกุมตามแนวทางที่ยืนยันแล้ว:

1. **Temp Staging & Copy & Verify:**
   - ทุกขั้นตอนการดาวน์โหลด แปลงไฟล์เสียง และฝัง Metadata/ปกอัลบั้ม จะทำในโฟลเดอร์ชั่วคราว (`Temp`) ในเครื่องคอมพิวเตอร์ก่อน
   - เมื่อไฟล์ผ่านการตรวจสอบจาก **Output Validator** ครบถ้วนแล้วเท่านั้น จึงจะคัดลอกไฟล์ (Copy & Verify) ไปยัง Micro SD Card เพื่อลดโอกาสเกิดไฟล์ขยะหรือไฟล์เขียนไม่สมบูรณ์บนการ์ดหากการ์ดหลุดกลางคัน (หมายเหตุ: Temp กับการ์ดอยู่คนละไดรฟ์ จึงไม่ใช่ Atomic Move จริง)
   - **กรณี Overwrite (DEC-040):** ให้คัดลอกไฟล์จาก Temp ไปเป็นชื่อชั่วคราวในโฟลเดอร์เดียวกันบนการ์ดก่อน (เช่น `<Title>.m4a.pladaz-tmp`) ตรวจสอบความสมบูรณ์ (Verify) แล้วจึงแทนที่ไฟล์เดิมด้วย `os.replace` หากเกิดข้อผิดพลาดหรือการ์ดหลุดระหว่างคัดลอก ให้ลบไฟล์ชั่วคราว โดยที่ไฟล์เดิมบนการ์ดยังคงอยู่ครบถ้วนไม่เสียหาย
   - ลบไฟล์ในโฟลเดอร์ `Temp` ทิ้งโดยอัตโนมัติเมื่องานเสร็จสิ้นหรือเมื่อเกิดข้อผิดพลาด
2. **การตรวจจับสถานะ Micro SD Card (`psutil` + Windows API):**
   - ตรวจสอบการเชื่อมต่อและพื้นที่ว่างก่อนเริ่มแต่ละเพลงในคิว และก่อนย้ายไฟล์จาก Temp เข้าสู่การ์ด
   - มีระบบเฝ้าดูสถานะการ์ดโดยตรวจสอบเป็นระยะ (Periodic check) ระหว่างการดาวน์โหลดและประมวลผลเพลง (DEC-041)
   - หากการ์ดถูกถอดระหว่างทำงาน ระบบจะหยุดคิวทันที แจ้งเตือนบน UI และไม่รายงานว่างานสำเร็จเด็ดขาด
3. **การบันทึก Log (`RotatingFileHandler`):**
   - บันทึกเหตุการณ์และข้อผิดพลาดลงไฟล์ Log แบบจำกัดขนาด (ป้องกันไฟล์ Log บวม) โดยไม่เปิดเผยข้อมูลส่วนบุคคลที่ไม่จำเป็น

## 9. แผนการทดสอบ (Test Strategy)

ต้องมีการทดสอบหลายระดับ และเชื่อมโยงผลทดสอบกับข้อกำหนดโดยตรง

### 9.1 ประเภทการทดสอบและเครื่องมือ

- **Unit Test:** ทดสอบกฎย่อย เช่น การสร้างเส้นทางโฟลเดอร์ การตัดความยาวชื่อ การแปลงอักขระต้องห้าม และการจัดการ Missing Metadata
- **Integration Test:** ทดสอบการทำงานร่วมกันของโมดูล เช่น Metadata Service (`mutagen` + `Pillow`) กับ `Output Validator`
- **File System Test:** ทดสอบสิทธิ์ พื้นที่ว่าง ชื่อซ้ำ การทำงานของ Temp Staging และการย้ายไฟล์
- **Device Test:** ทดสอบการเขียนและการอ่านไฟล์จาก Micro SD Card จริง
- **Compatibility Test:** ตรวจสอบว่าเครื่อง **SNOWSKY ECHO DAP** อ่านไฟล์ M4A, Metadata และปก 800x800 px ได้ตามเป้าหมาย
- **End-to-End Test:** ทดสอบกระบวนการตั้งแต่รับคำสั่งผ่าน UI จนได้ไฟล์ที่จัดเก็บตามโครงสร้าง
- **Regression Test:** รันทดสอบอัตโนมัติซ้ำหลังเปลี่ยนโค้ด เพื่อป้องกันไม่ให้ฟีเจอร์เดิมเสีย

เครื่องมือทดสอบและ Framework ที่ยืนยันแล้ว: **`pytest`**

### 9.2 Test Cases เบื้องต้น

### 9.3 เกณฑ์ผ่านการทดสอบ

- Test Case แต่ละรายการต้องมีสถานะจริง เช่น `Not Run`, `Pass`, `Fail`, `Blocked`
- ห้ามทำเครื่องหมาย `Pass` หากยังไม่ได้รันทดสอบและตรวจสอบผล
- บันทึกสภาพแวดล้อม รุ่นซอฟต์แวร์ ข้อมูลทดสอบ และหลักฐานที่เกี่ยวข้อง
- Test Case ที่ขึ้นกับข้อมูล TBA ให้ทำเครื่องหมาย `Blocked` หรือระบุข้อจำกัดอย่างชัดเจน

## 11. Acceptance Criteria — เกณฑ์ยอมรับงานเบื้องต้น

เกณฑ์ต่อไปนี้เป็นเป้าหมายที่ต้องตรวจสอบ ไม่ใช่การกล่าวว่าระบบทำได้แล้ว

1. แอปทำงานบน Windows ตามสภาพแวดล้อมที่กำหนด
2. ระบบสามารถบันทึกไฟล์เสียงในรูปแบบที่ได้รับการยืนยันว่าเป็นเป้าหมาย AAC
3. Metadata ที่กำหนดสามารถตรวจสอบกลับได้ตามรูปแบบไฟล์ที่อนุมัติ
4. ปกอัลบั้มถูกเก็บตามวิธีที่อนุมัติ
5. ผู้ใช้สามารถเลือกโฟลเดอร์ปลายทางบน Micro SD Card ได้
6. โครงสร้างโฟลเดอร์อิง Album Artist และ Album ไม่ใช่ Track Artist
7. มีระบบ **Download Queue** รองรับการดาวน์โหลดเพลงต่อเนื่อง พร้อมแสดงสถานะ Queued, Downloading, Completed และ Failed ชัดเจน
8. มีระบบ **Smart Folder Organizer** จัดการชื่อซ้ำ อักขระต้องห้ามของ Windows และกรณีไม่มี Album Artist ได้อย่างถูกต้อง
9. มีระบบ **SD Card Manager** ตรวจสอบพื้นที่ว่าง ตำแหน่งจัดเก็บ และแจ้งเตือนทันทีหากการ์ดถูกถอดระหว่างทำงาน
10. มีระบบ **Output Validator** ตรวจสอบความสมบูรณ์ของไฟล์เสียง AAC, Metadata (บังคับ `Title`) และปกอัลบั้ม (ตามหัวข้อ 7.5) ก่อนนับเป็น Completed
11. มีระบบ **Automated Regression Testing** รันตรวจสอบอัตโนมัติเมื่อแก้โค้ด โดยเฉพาะส่วนจัดโฟลเดอร์ Metadata ชื่อซ้ำ และการเขียนไฟล์
12. ระบบจัดการกรณีผิดพลาดโดยไม่รายงานความสำเร็จผิดพลาด
13. Test Cases ที่เป็นเกณฑ์บังคับผ่านตามหลักฐานการทดสอบ
14. ทดสอบความเข้ากันได้ของไฟล์ M4A (AAC-LC) และการอ่านข้อมูลแท็ก/ภาพปกกับเครื่องเล่นเป้าหมาย **SNOWSKY ECHO DAP** (Dual CS43198)
15. วิธีดาวน์โหลดและการใช้งานแหล่งข้อมูลผ่านการตรวจสอบสิทธิ์และเงื่อนไขที่เกี่ยวข้องก่อนนำไปใช้จริง

ค่าเชิงปริมาณ เช่น เวลาในการทำงาน ขนาดไฟล์สูงสุด หรืออัตราความสำเร็จ: **TBA**

1. อ่านเอกสารนี้ก่อนเสนอการเปลี่ยนแปลงที่มีผลต่อข้อกำหนดหรือสถาปัตยกรรม
2. ห้ามแต่งข้อเท็จจริง แหล่งอ้างอิง ความสามารถของอุปกรณ์ หรือผลการทดสอบ
3. ถ้าข้อมูลยังไม่ระบุ ให้ใช้ `TBA` อย่างชัดเจน
4. แยกข้อเท็จจริง ข้อเสนอ สมมติฐาน และผลการตรวจสอบออกจากกัน
5. หากต้องอาศัยข้อมูลภายนอก ให้ตรวจสอบจากแหล่งที่เชื่อถือได้ และบันทึกแหล่งอ้างอิงกับวันที่ตรวจสอบเมื่อเหมาะสม
6. หากเอกสารขัดแย้งกัน ห้ามเลือกคำตอบเอง ให้รายงานความขัดแย้งและขอการตัดสินใจ
7. ห้ามอ้างว่าโค้ดทำงานหรือ Test Case ผ่านแล้ว หากไม่ได้รันและตรวจสอบจริง

### 12.2 การรักษาข้อกำหนด

1. ห้ามเปลี่ยนหรือลบ Immutable Requirements โดยไม่ได้รับอนุญาตอย่างชัดเจนจากผู้ใช้
2. หากจำเป็นต้องเสนอการเปลี่ยนแปลง ให้แสดงข้อกำหนดเดิม เหตุผล ผลกระทบ และทางเลือกก่อน
3. ห้ามแทนที่ Album Artist ด้วย Track Artist ในกฎการจัดโฟลเดอร์
4. ห้ามตัด Metadata ที่ผู้ใช้ระบุออกจากเป้าหมายโดยพลการ
5. ห้ามเลือกเทคโนโลยีแทนผู้ใช้ในหัวข้อที่ยังเป็น TBA โดยไม่ระบุว่าเป็นข้อเสนอ
6. ห้ามเริ่มใช้วิธีดาวน์โหลดที่ยังไม่ได้รับการตรวจสอบด้านสิทธิ์และเงื่อนไขที่เกี่ยวข้อง

### 12.3 หลัก Software Engineering

1. ออกแบบให้แต่ละส่วนมีหน้าที่ชัดเจนและมีขอบเขตการพึ่งพาที่เหมาะสม
2. เลือก Design Pattern ตามความจำเป็น ไม่ใช้เพื่อความซับซ้อนโดยไม่มีเหตุผล
3. เขียน Test Cases สำหรับกฎธุรกิจและกรณีผิดพลาดที่สำคัญ
4. แก้ไขโค้ดแล้วต้องพิจารณาผลกระทบต่อ Test Cases และข้อกำหนดเดิม
5. หลีกเลี่ยงการผูกกฎธุรกิจเข้ากับ UI, ระบบไฟล์ หรือบริการภายนอกโดยไม่จำเป็น
6. บันทึกการตัดสินใจทางเทคนิคที่มีผลต่อการพัฒนาต่อในอนาคต

### 12.4 การอัปเดตเอกสาร

เมื่อมีการตัดสินใจใหม่:

- เปลี่ยน `TBA` เป็นข้อกำหนดที่ยืนยันแล้วเฉพาะเมื่อผู้ใช้หรือหลักฐานที่ได้รับอนุญาตยืนยัน
- อัปเดต Immutable Requirements โดยรักษาประวัติการเปลี่ยนแปลง
- เพิ่มหรือปรับ Test Cases ที่เกี่ยวข้อง
- บันทึกเหตุผลและผลกระทบของการเปลี่ยนแปลง
- ห้ามลบข้อมูลเดิมที่จำเป็นต่อการตรวจสอบย้อนกลับโดยไม่มีเหตุผล

## 14. ข้อสรุป

PLADAZ ได้รับการยืนยันข้อกำหนดหลักและสถาปัตยกรรมทางเทคนิคครบถ้วนสำหรับเริ่มการออกแบบและพัฒนาระบบ (Phase 1 เป็นต้นไป) ได้แก่ สถาปัตยกรรม Decoupled (`pywebview` + Python Core), การดาวน์โหลดและแปลงเสียงด้วย `yt-dlp` + `FFmpeg` เป็น M4A (AAC-LC) รองรับทั้งลิงก์เพลงเดี่ยว/Playlist/อัลบั้ม, การจัดการ Metadata 9 ฟิลด์ด้วย `mutagen` เสริมด้วย iTunes/MusicBrainz Search API และปก 1:1 JPEG 800x800 px สำหรับเครื่องเล่น **SNOWSKY ECHO DAP**, กฎการจัดโฟลเดอร์อัตโนมัติ การป้องกันไฟล์เสียบน Micro SD Card (Temp Staging & Copy & Verify) และชุดทดสอบอัตโนมัติด้วย `pytest` ส่วนด้านการออกแบบ UI (`TBA-019`) แยกอ้างอิงในเอกสาร Design Direction โดยตรงตามแนวทางที่ระบุไว้

สำหรับหัวข้อที่ผู้ใช้ยังข้ามการระบุไว้ ได้แก่ **เกณฑ์ตัวเลขประสิทธิภาพและขนาดไฟล์ที่ยอมรับได้ (`TBA-023`)**, **รายละเอียดการเทียบชื่อเพลง/ศิลปินกับผลค้นหา (`TBA-026`)** และ **ค่า Bitrate สำหรับ Fallback Encode (`TBA-027`)** เอกสารนี้ยังคงสถานะเป็น `TBA` อย่างเคร่งครัดตามกฎ ไม่มีการคาดเดาหรือเติมข้อมูลเอง

**กฎสูงสุด:** เมื่อข้อมูลไม่ชัดเจน ให้ถามหรือทำเครื่องหมาย `TBA` ห้ามสร้างข้อเท็จจริงขึ้นเอง และห้ามแก้ไข Immutable Requirements โดยไม่ได้รับอนุญาต
